# visitaudit-방문일정이탈점검

## 한 줄 요약

피험자별 방문 날짜 표와 프로토콜(방문창·선정/제외기준) 정의를 받아 **"이 시험이 계획대로 굴러가고 있는가"를 전수 대조**하는 오프라인 CLI. 방문창 이탈·순서 위반·결측 방문·중도탈락 처리를 날짜 산술로 판정하고, 그 결과를 그대로 **CONSORT 흐름도 숫자**와 **PP 집합 후보**, 그리고 논문 Methods/Results에 붙여넣을 KR/EN 문장 초안으로 내보낸다. 유효성 데이터는 한 줄도 필요 없다.

## 왜 필요한가

> 월간 모니터링 회의 전날 밤. SERENE 등록 트래커 엑셀을 열어 놓고, 피험자 47명 × 방문 5회 = 235행의 날짜를 눈으로 훑으면서 "V2가 창 안에 들어왔나"를 하나씩 뺄셈한다. 두 번 세면 두 번 다 숫자가 다르다. 그러다 그냥 "대략 3~4건 이탈"이라고 적고 회의에 들어간다.

BELL-001의 Phase-3 SERENE은 **지금 등록 단계이고 효능 데이터는 아직 없다**(DATA_INVENTORY). 즉 지금 이 시점에 카탈로그의 21개 툴 중 이 연구에 쓸 수 있는 것이 사실상 없다 — statwise·longistat·agreestat·metapool은 전부 결과 데이터가 나온 뒤의 툴이고, powerplan은 시작 전의 툴이다. **연구가 굴러가는 동안**을 다루는 툴이 하나도 없다.

지금은 대신 뭘 하는가: 엑셀에서 `=DATEDIF()` 를 손으로 깔거나, 정렬해 놓고 눈으로 본다. 그리고 이 작업은 매달 반복된다.

그리고 이 계산은 **논문 쓸 때 다시 한다.** 임상시험 논문의 CONSORT flow diagram과 "protocol deviations" 문단은 반드시 들어가야 하는 항목인데, 종료 후에 1년 치 엑셀을 거슬러 올라가 재구성하면 그때 나온 숫자는 모니터링 회의 때 보고한 숫자와 거의 항상 다르다. 등록이 진행되는 지금부터 같은 규칙으로 뽑아두면 그 불일치가 애초에 생기지 않는다.

지루하고, 전수 대조가 필요하고, 실수가 조용히 통과되고, 매달 반복된다. 사람이 가장 못하고 기계가 가장 잘하는 조합이다.

## 대안 대비 우위

| 대안 | 왜 그래도 이게 낫나 |
|---|---|
| **엑셀에서 손으로** (현재 방식) | 235행 날짜 뺄셈은 되긴 된다. 문제는 재현이 안 된다는 것 — 다음 달에 같은 파일로 다시 세면 숫자가 달라지고, 어느 쪽이 맞는지 알 방법이 없다. 이 툴은 규칙(프로토콜 JSON)을 파일로 고정하므로 같은 입력 → 항상 같은 숫자. |
| **EDC/CTMS의 data quality rule** (Medidata, REDCap 등) | 프로젝트마다 룰을 세팅해야 하고, 세팅 권한이 CRO에 있으면 "확인 요청 → 회신"이 며칠이다. 회의 전날 밤 22시에 쓸 수 있는 물건이 아니다. 이 툴은 CSV 하나면 30초. |
| **pip install 한 방** | 실제로 없다. lifelines·statsmodels 같은 대응물이 없는 영역이다. 통계 계산이 아니라 **프로토콜 대조**이므로, 라이브러리가 있을 수가 없다 — 규칙이 연구마다 다르기 때문. 그 규칙을 입력으로 받는 게 이 툴의 전부다. |
| **LLM에 붙여넣기** ← **여기가 핵심이다** | LLM은 235행의 날짜를 빼지 못하고, 빼지 못했다는 사실도 말하지 않는다. "이탈 4건으로 보입니다"라고 자신 있게 답하고, 그중 하나는 존재하지 않는 피험자다. 날짜 산술과 전수 카운트는 결정론적 코드가 이기는 몇 안 되는 영역이고, 여기가 정확히 그 영역이다. |

**기존 툴 대규모 개선 대신 신규 툴로 가는 이유(검토했음)**: joinaudit에 방문창 판정을 얹는 안, powerplan에 진행 모니터링을 얹는 안을 둘 다 검토했다. 둘 다 기각. joinaudit은 "파일을 합쳤을 때 누가 왜 빠졌나"를 답하는 툴이고, 여기에 프로토콜 개념을 넣으면 두 개의 서로 다른 질문이 한 리포트에 섞여 어느 쪽도 신뢰가 안 된다. powerplan은 데이터 파일을 입력으로 받지 않는 설계 단계 툴이라(pilot 제외) 성격이 정반대다. 경계를 흐리는 것보다 새 툴이 낫다.

### 인접 툴과의 경계

| | 답하는 질문 | 입력 | N이 줄어드는 이유 |
|---|---|---|---|
| `joinaudit` | 왜 최종 N이 이 숫자인가 — **파일 병합 상** | CSV 여러 개 | 키 불일치, 결측 파일, 중복 |
| `visitaudit` (이 툴) | 왜 최종 N이 이 숫자인가 — **프로토콜 상** | 방문 CSV + **프로토콜 JSON** | 창 이탈, 결측 방문, 중도탈락, 선정기준 위반 |

두 툴은 같은 CONSORT 상자를 서로 다른 쪽에서 채운다. 겹치지 않는다. 다만 **경계를 지키는 강제 장치**를 둔다: 프로토콜 JSON이 없으면 이 툴은 아무 판정도 하지 않고 exit 2로 죽는다. 프로토콜 없이 돌아가는 순간 joinaudit 재탕이 된다.

joinaudit의 `merged.csv`(피험자×시점)를 그대로 입력으로 받을 수 있게 한다 — 스키마 호환으로만 연결하고, 코드를 import 하거나 복사하지 않는다.

## 범위

### 한다 (v1)

1. **방문창 준수 판정** — 기준일(예: Baseline) + 오프셋 ± 창 으로 각 방문의 예정 구간을 계산하고, 실제 방문일이 안/밖/경계 중 어디인지 판정. 창 밖이면 며칠 밖인지까지.
2. **미도래·탈락후 분류** — `--as-of` 기준일 시점에 창이 아직 닫히지 않은 방문은 "미도래", 중도탈락일 이후 방문은 "해당없음". **둘 다 이탈로 세지 않는다.** (이 툴이 두 번 다시 안 열리게 되는 1순위 원인이 여기다.)
3. **순서·중복·불가능 날짜** — V3가 V2보다 앞선 경우, 같은 방문 2행, 등록일 이전 방문, 미래 날짜.
4. **결측 방문** — 필수 방문인데 기록이 없고 창이 이미 닫혔으면 결측. 탈락자면 결측이 아니라 탈락.
5. **선정/제외기준 재점검** — 프로토콜 JSON의 단순 규칙(`age >= 19`, `ISI_baseline >= 15`, `OSA진단 == Y` 등)을 스크리닝 CSV에 그대로 다시 적용해 위반자 색출.
6. **CONSORT 흐름 숫자** — 스크리닝 → 제외(사유별) → 무작위배정 → 군별 → 완료 → 분석대상(ITT/PP). 텍스트 다이어그램으로 출력.
7. **PP 집합 후보** — 프로토콜에 정의한 제외 규칙(필수방문 결측, 창이탈 N일 초과 등)을 적용해 PP에서 빠질 피험자 목록 + 사유. 판정이지 확정이 아님을 리포트에 명시.
8. **등록 진행** — 월별 등록 수, 현재 속도, 목표 N 도달 예상 시점(단순 선형, 불확실성 명시).
9. **커버리지 자백** — 피험자 몇 명 / 방문 몇 건을 판정했고 몇 건을 왜 판정 못 했는지 사유별로 리포트 머리에 출력. 판정률이 임계 미만이면 exit 3.
10. **문장 초안 KR/EN** — protocol deviation 문단, CONSORT 캡션 숫자, PP 정의 문장.

### 의도적으로 안 한다

- 유효성·안전성 분석 일체 (statwise / longistat / metapool 영역)
- 파일 병합 (joinaudit 영역)
- 이상반응 코딩 / MedDRA·CTCAE 매핑 — 사전이 없다. 심각도 판정을 흉내내면 위험하다.
- 무작위배정 목록 생성 — 별개 문제이고, 이 툴이 그걸 만들면 자기가 만든 걸 자기가 검사하는 꼴이 된다.
- 그림 — 텍스트 등록곡선/텍스트 CONSORT까지만 (stdlib 전용)
- EDC 연동, 네트워크 호출, 자격증명
- 결측 대치, 날짜 추정 — 기준일이 없으면 그 피험자는 통째로 "판정불가"이지, 추정하지 않는다.
- 시각/시분·타임존 — 날짜 단위로만 판정하고, 시각 정보가 있으면 버렸다고 자백한다.

## 입력 / 출력

### 입력

`방문기록.csv` (long, 1행 = 1 피험자-방문). `--wide` 로 1행 = 1피험자 형태도 허용. joinaudit `merged.csv` 도 그대로 받는다.

```
피험자ID,방문명,방문일,상태
BELL-0007,Screening,2026-03-02,완료
BELL-0007,Baseline,2026-03-16,완료
BELL-0007,V1,2026-04-13,완료
BELL-0007,V2,2026-05-18,완료
BELL-0008,Screening,2026-03-04,완료
BELL-0008,Baseline,2026-03-18,완료
BELL-0008,V1,2026-04-30,완료
```

`프로토콜.json`

```json
{
  "연구명": "SERENE",
  "기준방문": "Baseline",
  "목표N": 120,
  "방문": [
    {"이름": "Screening", "오프셋": -14, "창": [-28, -1], "필수": true},
    {"이름": "Baseline",  "오프셋": 0,   "창": [0, 0],    "필수": true},
    {"이름": "V1",  "오프셋": 28, "창": [-3, 3], "필수": true},
    {"이름": "V2",  "오프셋": 56, "창": [-5, 5], "필수": true},
    {"이름": "EOT", "오프셋": 84, "창": [-7, 7], "필수": true}
  ],
  "선정기준": [
    {"항목": "age", "연산": ">=", "값": 19},
    {"항목": "age", "연산": "<=", "값": 65},
    {"항목": "ISI_baseline", "연산": ">=", "값": 15}
  ],
  "제외기준": [
    {"항목": "OSA진단", "연산": "==", "값": "Y"}
  ],
  "PP제외규칙": {"필수방문결측": true, "창이탈일수초과": 7}
}
```

선택 입력 `피험자.csv` — `피험자ID, 군, 등록일, 탈락일, 탈락사유, age, ISI_baseline, OSA진단 …`

### 실행 예

```bash
python -m visitaudit 방문기록.csv \
  --protocol 프로토콜.json \
  --subjects 피험자.csv \
  --as-of 2026-08-14 \
  --out-dir 결과_202608
```

`--as-of` 는 필수에 가깝게 취급한다(미지정 시 오늘로 두되 리포트에 크게 박는다). 이게 있어야 "미도래" 판정이 재현 가능해진다.

### 출력

```
visitaudit — 방문일정 이탈 점검
연구: SERENE   기준시점(as-of): 2026-08-14   프로토콜: 프로토콜.json

[커버리지 자백]
  피험자 47명 중 45명 판정 / 2명 판정불가
    - 기준방문(Baseline) 날짜 없음: 2명 (BELL-0031, BELL-0044) → 추정하지 않음
  방문 235건 중 198건 판정 / 37건 판정 제외
    - 미도래(창 미마감): 29건   - 탈락 이후: 6건   - 날짜 파싱 실패: 2건
  판정률 84.3% (임계 70%) → 통과
  * 시각 정보 12건 발견, 날짜 단위로만 판정함

[이탈]  총 6건 (판정 대상 198건 중 3.0%)
  창 이탈  4건
    BELL-0008  V1   예정 2026-04-15 (창 04-12~04-18)  실제 04-30  → +12일
    BELL-0019  V2   예정 2026-06-02 (창 05-28~06-07)  실제 06-14  → +7일
    BELL-0022  EOT  예정 2026-07-01 (창 06-24~07-08)  실제 07-16  → +8일
    BELL-0040  V1   예정 2026-07-20 (창 07-17~07-23)  실제 07-25  → +2일
  필수방문 결측  1건
    BELL-0013  V2   창 2026-05-11~05-21 마감, 기록 없음, 탈락 기록도 없음
  순서 위반  1건
    BELL-0026  V2(2026-06-09) 가 V1(2026-06-20) 보다 앞섬

[선정/제외기준 재점검]  위반 1건
    BELL-0035  ISI_baseline = 13  (선정기준 >= 15)

[CONSORT]
  스크리닝 62 → 제외 15 (기준미달 9 / 동의철회 4 / 기타 2)
  무작위배정 47  →  중재군 24 / 대조군 23
  완료 21 / 20      중도탈락 3 (이상반응 1, 추적불가 2) / 3 (동의철회 3)
  ITT 47   PP 후보 41  (제외 6: 창이탈 7일초과 3, 필수방문결측 1, 선정기준위반 1, 탈락 1 — 중복 1명 제거)

[등록 진행]
  3월 12 / 4월 9 / 5월 8 / 6월 10 / 7월 8 명 (최근 3개월 평균 8.7/월)
  목표 120명까지 73명 → 현 속도 유지 시 2027-04 경 (단순 선형 외삽, 신뢰구간 아님)

출력: 결과_202608/진행점검.md, 이탈목록.csv, 피험자별요약.csv, CONSORT.txt
exit 1 (이탈 발견)
```

- `진행점검.md` — 위 리포트 전문 + KR/EN 문장 초안
- `이탈목록.csv` — `피험자ID, 방문명, 이탈유형, 예정일, 창시작, 창종료, 실제일, 창밖일수, 심각도, 근거`
- `피험자별요약.csv` — `피험자ID, 군, 완료방문수, 이탈건수, 최대창밖일수, PP포함여부, PP제외사유, 판정가능여부`
- `CONSORT.txt` — 텍스트 흐름도

**exit code**: 0 이탈 없음 / 1 이탈 발견 / 2 입력·프로토콜 오류 (프로토콜 JSON 없으면 여기) / 3 판정불가(판정률 임계 미만 — 조용히 통과시키지 않는다)

## 완료 기준 (빌더가 만족시켜야 하는 체크리스트)

- [ ] `dependencies = []` — stdlib 전용, 네트워크 호출 0
- [ ] 입력 파일은 읽기 전용, 모든 산출물은 `--out-dir` 안에만
- [ ] 프로토콜 JSON 미지정 시 exit 2 로 즉시 중단 (joinaudit 재탕 방지 장치)
- [ ] 날짜 파서: `2026-03-02` / `2026/03/02` / `2026.3.2` / `20260302` / 엑셀 시리얼 정수 / `2026-03-02 14:30` (시각 버림 + 자백) 각각 테스트
- [ ] 창 경계 포함 규칙을 문서에 명시하고 테스트: `창 [-3, 3]` 이면 예정일 -3일과 +3일은 **창 안**
- [ ] **미도래 판정**: `--as-of` 기준으로 창 종료일이 아직 안 지난 방문은 이탈로 세지 않음 — 합성 데이터에 미래 방문 3건을 심어 이탈 0건이 나오는 테스트

## 실패할 수 있는 지점 (그리고 가장 싸게 조기 발견하는 법)

1. **방문일정 데이터가 CRO/EDC에만 있고 사용자 손에는 없다.** 그러면 이 툴은 입력이 없어 죽은 툴이 된다.
   → **가장 싼 조기 확인**: 빌드 첫 30분에 실제 SERENE 등록 트래커(엑셀이든 뭐든)를 열어 `피험자ID` + `방문일` 두 열이 존재하는지만 본다. 없으면 즉시 방향을 틀어 CONSORT 숫자 + 선정기준 재점검만 남긴 축소판으로 간다(스크리닝 로그는 거의 확실히 손에 있다).

2. **프로토콜에 방문창(visit window)이 애초에 명시돼 있지 않다.** 한국 중소 DTx 임상에서 드물지 않다.
   → **가장 싼 조기 확인**: 프로토콜 문서에서 visit window 표를 5분 안에 못 찾으면, 창 기본값을 `[0,0]` 으로 두고 리포트에 "창 미정의 — 이탈 판정 불가"를 크게 박는다. 창이 없으면 결측·순서·CONSORT만으로도 툴은 산다.

3. **크라잉울프.** 미도래 방문과 탈락후 방문을 이탈로 세는 순간, 첫 실행에서 "이탈 37건"이 뜨고 사용자는 두 번 다시 이 툴을 열지 않는다.
   → **가장 싼 조기 확인**: 가장 먼저 쓰는 테스트가 "미래 방문 3건 + 탈락후 방문 2건을 심고 이탈 0건" 테스트다. 이게 통과하기 전엔 다른 기능을 붙이지 않는다.

4. **애초에 필요 없었을 가능성.** 피험자 20명 × 5방문이면 엑셀로 30분이면 끝난다. N이 작으면 가치가 급감한다.
   → **가장 싼 조기 확인**: 실제 등록 N을 확인한다. `N × 방문수 < 100` 이면 매달 쓰는 모니터링 툴로서의 가치는 포기하고, **논문 작성 시점의 CONSORT/PP 재현성**을 중심에 두고 그쪽 출력을 두껍게 만든다. 그 가치는 N이 작아도 남는다 (숫자가 회의록과 논문에서 달라지는 문제는 N=20에서도 똑같이 생긴다).

5. **joinaudit 재탕처럼 보인다.** 리포트가 "누가 빠졌나" 목록으로 보이기 시작하면 사용자 눈에는 같은 툴이다.
   → **가장 싼 조기 확인**: 프로토콜 JSON 없이는 exit 2로 죽게 만든다(완료 기준에 포함). 그리고 리포트 첫 화면을 "이탈 건수 + CONSORT"로 시작한다 — 피험자 목록이 아니라.

## 빌더를 위한 메모

- **버리는 순서** (시간 부족 시): 등록곡선 외삽 → `--wide` 입력 → 선정/제외기준 재점검 → PP 후보 산출 → 문장 초안. 이 순서로 잘라도 툴은 산다.
- **절대 버리면 안 되는 2가지**:
  1. **미도래/탈락후를 이탈로 세지 않는 규칙.** 이게 무너지면 이 툴은 한 번 열리고 끝난다.
  2. **커버리지 자백 + exit 3.** 판정 못 한 방문을 조용히 "이상 없음"으로 흘려보내는 체커는 없느니만 못하다.
- 규칙은 넓히지 말고 좁힌다. 애매하면 이탈이 아니라 판정불가로 보낸다.
- `--as-of` 를 리포트 헤더와 모든 CSV에 박아라. 같은 파일을 다음 달에 다시 돌리면 결과가 달라지는 게 정상이고, 왜 달라졌는지는 이 한 줄이 설명한다.
- 다른 툴 폴더를 수정·import·복사하지 않는다. joinaudit 연동은 `merged.csv` 스키마를 읽을 수 있다는 것뿐이다.
