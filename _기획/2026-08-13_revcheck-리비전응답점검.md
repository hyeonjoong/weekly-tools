# revcheck-리비전응답점검

## 한 줄 요약

**제출본 · 개정본 · 응답서(point-by-point response) 세 파일을 동시에 읽어**, 응답서에 적은 약속이 개정 원고에 실제로 반영됐는지, 답 안 한 리뷰어 코멘트는 없는지, 아무에게도 말하지 않고 슬쩍 바꾼 곳은 없는지를 기계적으로 대조하는 도구.

## 왜 필요한가

> 리비전 마감 D-1 밤 11시. 리뷰어 3명 × 코멘트 8개 + 에디터 코멘트 2개 = 26건.
> 응답서에는 "We have revised this sentence (p.7, lines 210–214)" 같은 문장이 20군데 들어가 있고,
> 그중 절반은 인용부호 안에 **개정 후 문구를 그대로 붙여넣어** 놨다.
> 그런데 그 뒤로 공저자 코멘트를 반영해 원고를 두 번 더 고쳤다.
> 응답서에 인용해 둔 문구가 지금 원고에 아직 그대로 있는지, 아무도 모른다.

이 상황에서 지금 하는 일은 이렇다. 응답서를 한 화면에 띄우고 개정본을 다른 화면에 띄운 다음, Ctrl+F로 한 건씩 찾는다. 26건을 다 하기엔 시간이 없으니 "중요해 보이는 것"만 골라 확인하고 나머지는 믿고 넘긴다. 줄번호는 애초에 맞을 리가 없다고 생각하고 확인조차 안 한다.

**여기서 나는 사고는 전부 조용하다.** 응답서는 매끄럽게 읽히고, 개정본도 멀쩡하고, 투고 시스템은 아무 말 없이 접수한다. 문제는 리뷰어가 응답서를 손에 들고 원고를 열었을 때 처음 드러난다:

- 리뷰어 2-5번 코멘트에 **아예 응답이 없다** (번호가 2-4 다음 2-6으로 건너뛴다). 가장 흔하고 가장 치명적이다.
- "다음과 같이 수정했습니다"라며 인용한 문장이 **개정본에 없다**. 그 뒤에 또 고쳤기 때문이다. 리뷰어 입장에선 저자가 거짓말을 한 것으로 보인다.
- "p.7, line 210" 참조가 **엉뚱한 곳**을 가리킨다. 문단이 밀렸기 때문이다.
- 리뷰어가 요청하지도 않았는데 **Results의 숫자가 바뀌어 있다.** 재분석했으면 밝혔어야 한다. 밝히지 않으면 데이터 조작 의심을 산다.
- "새 참고문헌 3편을 추가했다"고 썼는데 실제로는 2편만 들어갔다.

이건 사람이 가장 못하고 기계가 가장 잘하는 조합이다. 세 문서를 동시에 들고 26 × 5가지를 전수 대조하는 일은 새벽 1시의 사람이 절대 못 한다. **그런데 diff와 문자열 대조는 기계가 완벽하게 한다.**

## 대안 대비 우위

| 대안 | 왜 이걸로 안 되나 |
|---|---|
| **Word 변경내용 추적 / 문서 비교** | 무엇이 바뀌었는지는 보여준다. 그러나 **응답서를 읽지 않는다.** "바뀐 것 중 응답서가 언급하지 않은 것"과 "응답서가 약속했는데 안 바뀐 것"이 정확히 우리가 알고 싶은 것인데, 문서 비교는 그 교집합을 못 만든다. 게다가 변경점 400개를 눈으로 훑는 건 확인이 아니라 체념이다. |
| **눈으로 Ctrl+F 대조** | 26건 × 5종 = 130회 확인. 실제로는 절반쯤 하다 만다. 그리고 사람은 "빠진 번호"를 못 본다 — 있는 것만 보이고 없는 것은 안 보인다. |
| **LLM에 세 파일 붙여넣기** | **여기가 핵심이다.** LLM은 "응답서에 인용된 문구가 개정본에 문자 그대로 있는가"를 대조하지 못한다. 비슷하면 있다고 말한다. 코멘트 번호를 전수로 세지 못하고, 세지 못했다는 사실도 말하지 않는다. 26건 중 19건만 보고도 "모두 반영되었습니다"라고 답한다. 정확히 이 지점 때문에 numcheck가 존재한다. 같은 논리다. |
| **저널 제출 시스템** | 아무것도 검사하지 않는다. 파일을 받을 뿐이다. |
| **공저자 검토** | 공저자는 내용을 본다. 문구 일치·번호 누락은 아무도 안 본다. |

### 인접 툴과의 경계

이 저장소는 이미 원고 3종 세트(numcheck / draftcheck / citecheck)를 갖고 있다. **네 번째를 끼워 넣는 것이므로 경계를 명확히 못박는다.**

| 툴 | 보는 것 | 문서 수 | 언제 |
|---|---|---|---|
| **numcheck** | 원고 안 **숫자의 산술**이 맞는가 | 1개 | 투고 직전 |
| **draftcheck** | 원고가 **자기 안에서** 앞뒤가 맞는가(인용↔참고문헌, 그림표 번호, 약어, 분량) | 1개 | 투고 직전 |
| **citecheck** | 참고문헌이 **실존**하는가(DOI·철회) | 1개(+네트워크) | 투고 직전 |
| **revcheck (이 툴)** | **응답서의 약속과 개정본의 실제가 일치하는가** | **3개(제출본·개정본·응답서)** | **리비전 직전** |

**revcheck는 원고 한 개를 혼자 검사하지 않는다.** 개정본 자체의 숫자·인용·번호 검사는 전부 기존 3종의 몫이고, revcheck는 리포트 끝에 "개정본에 numcheck와 draftcheck를 따로 돌리세요"라고 안내만 한다. 반대로 기존 3종은 두 번째 파일을 받지 않으므로 diff를 절대 못 한다. **겹치는 코드는 0줄이어야 한다** — 원고 파서도 복사하지 말고 이 폴더 안에 다시 쓴다.

## 범위

### 한다 (v1)

1. **세 파일 읽기** — `--old`(최초 제출본), `--new`(개정본), `--response`(응답서). 각각 `.docx` / `.md` / `.tex` / `.txt`. docx는 zipfile+ElementTree로 직접 파싱(표 셀 포함). **변경내용 추적(w:ins/w:del)이 켜져 있으면 감지해서 "수락본 기준으로 읽었다 / 원본 기준으로 읽었다"를 리포트 첫머리에 반드시 명시한다.** 조용히 한쪽만 읽고 넘어가지 않는다.

2. **리뷰어 코멘트 번호 전수 점검** — 응답서에서 코멘트 식별자를 추출한다. 지원 패턴: `Reviewer 1, Comment 3` / `R1-3` / `1-3` / `Comment 3:` / `Reviewer #2` 하위 `1)`,`2)` 중첩 / `Editor` 블록 / 한국어 `심사위원 1 - 3`. 점검 내용: **번호 건너뜀**(2-4 다음 2-6), **중복 번호**, **응답 본문이 비어 있거나 30자 미만**, 리뷰어별 코멘트 수 요약. 번호 체계를 못 잡으면 추측하지 말고 **종료코드 3(판정불가)** 로 멈춘다.

3. **인용 문구 실존 검증 — 이 툴의 존재 이유.** 응답서 안에서 "개정 후 문구"로 제시된 인용(따옴표 `" "` `“ ”` `『 』`, 블록 인용 `>`, 이탤릭 단락, `Revised text:` 뒤 문장)을 뽑아, **개정본에 문자 그대로 존재하는지** 대조한다. 비교 전 정규화: 연속 공백 1칸, 곧은/굽은 따옴표 통일, 하이픈/대시 통일, 줄바꿈 제거, 서식 태그 제거. 일치하면 통과, 부분 일치(80% 이상, difflib 비율)면 **경고 + 실제 개정본 문구 나란히 출력**, 전혀 없으면 **치명**. 15자 미만의 짧은 인용은 우연 일치가 많으므로 검사에서 제외하고 커버리지 자백에 사유와 함께 기록한다.

4. **위치 참조 검증** — `p. 7, lines 210–214` / `page 7` / `L210` / `7쪽 210줄` 형태를 추출한다. `.md`/`.txt`/`.tex`는 줄 번호가 실재하므로 (a) 개정본 총 줄 수 범위 안인지, (b) 그 줄이 **실제로 old→new에서 변경된 구간인지** 검사한다. `.docx`는 줄 번호가 파일에 존재하지 않으므로 **추정하지 않고 "확인불가"로 강등**하고, 참조 건수만 보고한다. 페이지 참조도 마찬가지로 확인불가다. 여기서 정직하게 지는 것이 지어내는 것보다 낫다.

5. **"수정했다"는데 안 바뀐 곳 탐지** — 응답 블록 안에 변경 주장 키워드(`revised`, `changed`, `added`, `modified`, `rewritten`, `수정했`, `추가했`, `반영했`)가 있는데, 그 블록에 딸린 인용 문구도 없고 위치 참조도 없어 검증 수단이 하나도 없으면 **"검증 불가한 변경 주장"** 으로 별도 집계한다. 그리고 **old와 new의 전체 문단 diff가 0인데 변경 주장이 1건 이상이면 즉시 치명** — 개정본 대신 제출본을 실수로 첨부한 사고를 여기서 잡는다.

6. **미신고 변경(stealth edit) 목록** — `difflib.SequenceMatcher`로 문단 단위 정렬 후 변경/추가/삭제된 문단을 뽑고, 각 문단이 응답서 어디에서도 언급되지 않았으면 목록에 올린다. 등급 규칙: **변경 전후로 숫자(정수·소수·백분율·p값)가 달라진 문단은 치명**, Results/Abstract 절의 변경은 경고, Introduction/Discussion의 문장 다듬기는 정보. 숫자 변경 문단은 리비전 사고 중 가장 값비싼 것이므로 절대 정보 등급으로 내리지 않는다.

7. **참고문헌 · 그림 · 표 증감 대조** — old/new의 참고문헌 목록, Figure/Table 번호 목록을 각각 뽑아 추가·삭제분을 낸다. 응답서가 "added N references / new Table 3"이라고 말한 수량과 실제 증감이 다르면 경고. 추가된 문헌은 `추가문헌.csv`로 내보내며 **열 스키마는 citecheck 입력과 동일**하게 맞춘다(새로 넣은 문헌이야말로 DOI 검증이 안 된 문헌이다).

8. **분량 변화 정보** — 초록·본문 단어수, 참고문헌 수, 그림표 수의 old→new 변화를 정보 등급으로 한 줄 출력. 저널 한도 판정은 하지 않는다(draftcheck 몫).

9. **커버리지 자백(필수 출력)** — 코멘트 N건 중 응답 확인 M건 / 인용 문구 후보 P건 중 대조 Q건 / 건너뜀 K건과 **사유별 내역**. 이 블록 없이는 리포트를 출력하지 않는다.

### 의도적으로 안 한다

- **응답의 내용적 타당성을 판단하지 않는다.** 리뷰어가 만족할지, 반박이 설득력 있는지는 사람의 일이다. 이 툴은 "약속한 것이 실제로 있는가"만 본다.
- **응답서를 작성해 주지 않는다.** 문장 생성은 이 저장소의 일이 아니다.
- **개정본 자체의 정합성을 검사하지 않는다.** 숫자→numcheck, 인용↔참고문헌·그림표 번호·약어→draftcheck, DOI→citecheck. 리포트 끝에 안내 한 줄만 넣는다.
- **변경내용 추적 마크업을 생성하지 않는다.** 읽기만 하고 쓰지 않는다.
- **PDF를 읽지 않는다.** stdlib만으로 한 세션 안에 못 끝내고, 반쯤 되는 파서는 커버리지를 거짓말로 만든다.
- **영문 교정·문법·표절 검사를 하지 않는다.**
- **의미 기반 매칭을 하지 않는다.** "비슷한 문장"을 찾아주지 않는다. 정규화 후 문자열 일치와 difflib 비율만 쓴다. 유사도로 판정을 시작하는 순간 이 툴은 LLM의 열등한 복제품이 된다.
- **네트워크를 쓰지 않는다.** 호출 0건.
- **원본 파일을 절대 수정하지 않는다.**

## 입력 / 출력

### 입력

세 파일. 응답서는 보통 이런 모양이다:

```
Reviewer 1

Comment 1-1: The sample size justification is unclear.
Response: We thank the reviewer. We have added the power calculation
to the Methods (p. 5, lines 132-140): "Assuming a between-group
difference of 3.0 points on the ISI with SD 4.5, 42 participants per
arm provide 80% power at a two-sided alpha of 0.05."

Comment 1-2: Please report the dropout rate by arm.
Response: Revised as suggested. See Table 2.
```

### 실행 예

```bash
python3 -m revcheck.cli \
  --old 제출본.docx --new 개정본.docx --response 응답서.docx \
  --out-dir 결과
```

### 출력

```
revcheck — 리비전 응답 점검
읽기: 제출본.docx(문단 214) / 개정본.docx(문단 227) / 응답서.docx
      ※ 개정본에 변경내용 추적 흔적이 있습니다 — 모두 수락된 상태로 읽었습니다.

[치명 3건]
1. 응답 2-5 에 대한 응답 블록이 없습니다. (응답서에서 2-4 다음이 2-6입니다)
2. 응답 1-1 이 인용한 문구가 개정본에 없습니다.
   응답서: "...42 participants per arm provide 80% power at a two-sided alpha of 0.05."
   개정본에서 가장 가까운 문장(일치율 91%):
           "...45 participants per arm provide 80% power at a two-sided alpha of 0.05."
   → 숫자가 다릅니다. 응답서와 원고 중 어느 쪽이 최신인지 확인하세요.
3. 미신고 변경 — 응답서 어디에도 언급되지 않았는데 숫자가 바뀐 문단이 1건 있습니다.
   Results 3번째 문단: "mean ISI decreased by 5.2 (SD 3.1)" → "5.8 (SD 3.4)"

[경고 4건]
4. 응답 3-2 의 변경 주장("we have added")을 검증할 수단이 없습니다 (인용 문구도, 위치 참조도 없음).
5. 응답서는 참고문헌 3편 추가라고 했으나 실제 증가는 2편입니다. (추가문헌.csv 참조)
6. 미신고 변경 — Discussion 2문단이 응답서 언급 없이 수정되었습니다.
7. 위치 참조 6건은 .docx라 줄 번호를 확인할 수 없습니다 (건수만 보고).

[정보]
- 본문 단어수 4,120 → 4,388 (+268), 참고문헌 41 → 43, Table 3 → 4 (Table 4 신규)

[커버리지 자백]
- 리뷰어 코멘트 식별: 26건 (R1 8 / R2 9 / R3 7 / Editor 2)
- 응답 블록 확인: 25건 / 누락 1건
- 인용 문구 후보 20건 → 대조 17건 (건너뜀 3건: 15자 미만 2건, 표 안 인용 1건)
- 위치 참조 6건 → 검증 0건 (docx: 줄 번호 부재)

※ 개정본 자체의 숫자·인용·번호는 검사하지 않았습니다. numcheck와 draftcheck를 따로 돌리세요.

종료코드 1 (치명 있음)
결과/리비전점검.md, 문제목록.csv, 변경목록.csv, 추가문헌.csv 저장
```

## 실패할 수 있는 지점 (그리고 가장 싸게 조기 발견하는 법)

1. **응답서 형식이 너무 자유로워 코멘트를 하나도 못 잡는다.** 응답서는 저널마다·사람마다 형식이 다르고, 표로 만든 사람도 있다. 코멘트를 못 잡으면 이 툴의 8할이 죽는다.
   → **가장 싼 조기 확인**: 빌드 **첫 30분 안에** 파서만 먼저 만들어 본인의 실제 응답서 1~2개에 돌려 본다. 식별된 코멘트 수가 실제 수와 맞는지만 본다. 3종 이상 패턴이 안 잡히면 **v1 범위를 "번호 목록을 `--comments 1-1,1-2,...` 로 직접 받는 모드"까지 축소**한다. 추측 파싱으로 억지로 채우지 말 것.

2. **인용 문구 대조가 거짓 양성 폭탄이 된다.** docx는 같은 문장을 `<w:r>` 여러 개로 쪼개고, 워드가 따옴표·하이픈을 자동 변환하며, 저자가 인용하며 `[...]`로 줄이거나 앞뒤를 조금 다듬는다. 이러면 멀쩡한 응답서에서 치명이 10건 뜨고, 그 순간 이 툴은 두 번 다시 안 열린다.
   → **가장 싼 조기 확인**: 깨끗한 대조본을 만들 때 **일부러 워드에서 저장한 docx**를 쓴다. 여기서 치명이 1건이라도 나오면 **규칙을 넓히지 말고 좁힌다** — 일치율 임계를 올리고, `[...]` 포함 인용과 15자 미만은 검사 대상에서 빼고 커버리지 자백에 사유를 적는다. 애매하면 치명이 아니라 경고다.

3. **미신고 변경 목록이 소음이 된다.** 리비전은 원래 많이 고친다. 문단 200개 중 60개가 바뀐 원고에서 "언급되지 않은 변경 60건"을 나열하면 아무도 안 읽는다.
   → **가장 싼 조기 확인**: 실제 리비전 쌍 하나로 변경률부터 재 본다. 30%를 넘으면 **숫자 변경 문단만 개별 나열하고 나머지는 절별 카운트 요약으로 강등**한다. 이 항목의 가치는 "숫자가 조용히 바뀐 곳"에 거의 전부 몰려 있다.

4. **위치 참조 검증이 .docx에서 통째로 무의미하다.** 실무 원고의 대부분이 docx다. 그러면 항목 4는 "확인불가 6건"만 출력하는 죽은 기능이 된다.
   → **가장 싼 조기 확인**: 이건 이미 알고 시작한다. 그래서 항목 4는 **버리는 순서 1번**이다. 다른 항목이 시간을 잡아먹으면 "참조 건수만 세어 정보 등급으로 보고"까지만 남기고 잘라낸다. 대신 **확인불가를 이상 없음으로 절대 표시하지 않는다** — 조용히 통과시키는 체커는 없느니만 못하다.

5. **이 툴이 애초에 필요 없었을 시나리오** — 최근에 낸 리비전 3종 세트에 돌렸는데 치명 0건, 경고도 형식적인 것뿐이라면, 이 사람은 원래 리비전을 꼼꼼히 하는 사람이고 이 툴은 안 열린다.
   → **가장 싼 조기 확인**: **1일차에 항목 2(코멘트 번호 전수)와 항목 3(인용 문구 대조)만 먼저 만들어** 실제 리비전 1건에 돌린다. **30초면 안다.** 여기서 0건이면 나머지를 만들지 말고 접는다.

## 빌더를 위한 메모

- 폴더 `revcheck-리비전응답점검/`, 패키지 `revcheck`, CLI `revcheck`. `[project.scripts]` 등록 + `python3 -m revcheck.cli` 항상 동작. 슬러그 충돌 먼저 확인.
- **기존 툴 폴더 절대 수정 금지, 코드 import 금지, 복사 금지.** draftcheck의 docx 파서를 참고는 하되 이 폴더 안에 다시 쓴다. 통합은 `추가문헌.csv` 열 스키마 호환으로만 한다.
- diff는 `difflib.SequenceMatcher` 문단 단위 정렬 + 변경 문단 내 문장 단위 세부. 전부 stdlib다. 문단 정렬 키는 정규화된 텍스트로 하고, 절(section) 태깅은 헤딩 텍스트 기반으로 단순하게.
- **버리는 순서**: ①위치 참조 검증(항목 4) → ②분량 변화 정보(항목 8) → ③참고문헌/그림표 증감(항목 7) → ④미신고 변경 중 비숫자 문단.
- **절대 버리면 안 되는 것 2가지**: **코멘트 번호 전수 점검(항목 2)** 과 **인용 문구 실존 검증(항목 3)**. 이 둘이 이 툴의 존재 이유다. 나머지는 전부 곁가지다.
- 출력 언어는 한국어. 응답서·원고가 영문이어도 지적 문장은 한국어로 쓰고 인용문은 원문 그대로 보여준다.
