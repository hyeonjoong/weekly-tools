# draftcheck-원고투고점검

## 한 줄 요약

투고 직전 원고 파일(.docx/.md/.tex) 하나를 받아, **사람이 눈으로는 절대 못 잡는 기계적 정합성 오류**
— 본문 인용과 참고문헌 목록 불일치, Figure/Table 번호 누락·순서 뒤바뀜, 초록/본문/표 사이 숫자(N, p, 백분율) 불일치,
정의 없이 쓰인 약어, 효과크기·CI 없이 p값만 있는 문장, 단어수 초과 —
를 전수 대조해 **줄번호가 붙은 수정 목록**으로 뱉는 오프라인 CLI.

---

## 왜 필요한가

**트리거 모먼트 (아주 구체적으로):**
> 공저자 코멘트를 다 반영하고, 저널 사이트에 업로드하기 직전 30분. 또는 리비전 원고를 다시 올리기 직전.
> "참고문헌 번호 안 밀렸나? Figure 3 본문에서 언급했나? 초록 N이랑 Table 1 N이랑 맞나?"가 불안해지는 그 순간.

**지금은 대신 뭘 하는가:** Ctrl+F를 서른 번 누른다. 참고문헌 목록을 스크롤하며 본문 인용 번호와 눈으로 대조한다.
초록 숫자와 표 숫자를 번갈아 본다. 대부분은 **그냥 안 한다** — 시간이 없어서. 그리고 desk reject 사유나
리뷰어 1번 코멘트("Reference 27 is not cited in the text", "Figure 3 is never referred to")로 되돌아온다.

이 확인 작업의 성질이 중요하다: **지루하고, 전수 대조가 필요하고, 실수가 조용히 통과되고, 리비전마다 반복된다.**
사람이 가장 못하고 기계가 가장 잘하는 조합이다. 그리고 이 저장소의 17개 툴 중 **원고 파일 자체를 여는 툴은 하나도 없다.**

IDEAS.md의 사용자 본인 힌트가 이 방향을 직접 가리킨다:
"자주 반복하는 귀찮은 작업: 특별히 없음 (단, **논문 작업은 루틴하게 자주 함**)",
"현재/다가오는 방향: 논문 작업 루틴 + 새 논문 주제 발굴과 **신규 논문 작성**까지 돕는 툴 선호".
카탈로그는 논문의 **앞단**(paperforge=아이디어, pubgap=연구공백)과 **분석단**(statwise/table1/metapool 등)은 두껍게 덮었지만,
**쓰고 내는 단계는 완전히 비어 있다.** 이 툴은 그 빈칸의 첫 칸이다.

## 대안 대비 우위

| 대안 | 실제로 잡아주는 것 | 왜 이게 이기는가 |
|---|---|---|
| **눈으로 Ctrl+F** | 이론상 전부 | 참고문헌 60개 × 본문 인용 200개 교차 대조를 사람이 정확히 못 한다. 게다가 리비전마다 처음부터 다시. 실제로는 그냥 생략됨. |
| **EndNote / Zotero 필드** | 인용–목록 동기화 | 필드를 걸어 쓴 원고에서만 작동. 공저자가 필드를 깨뜨리거나 수기로 `[12]`를 타이핑한 순간 무력화. Figure/Table 번호, 숫자 일관성, 약어, 통계 보고는 **아예 범위 밖**. |
| **Word 맞춤법/Grammarly** | 문법·표현 | 정합성은 문법이 아니다. `[27]`이 목록에 없다는 걸 Grammarly는 모른다. |
| **저널 자체 업로드 검사** | 서식·파일형식 | 통과시켜 놓고 리뷰어가 잡는다. 그때는 이미 늦다. |
| **LLM에게 원고 붙여넣고 "확인해줘"** | 인상적인 요약 | **여기가 핵심이다.** LLM은 참고문헌 60개를 세지 못하고 조용히 지어낸다. "27번 인용 없음"을 놓치거나, 있지도 않은 문제를 만들어낸다. 전수 대조·계수(counting)는 결정론적 파싱이 압도적으로 옳다. 이 툴이 존재하는 이유가 바로 이것이다. |
| **pip install 가능한 기존 라이브러리** | — | 이 문제를 통째로 푸는 패키지는 사실상 없다(`docx2txt`, `pybtex` 등은 부품일 뿐). 게다가 이 저장소는 `dependencies = []`가 규약이고, **.docx는 stdlib `zipfile`+`xml.etree`만으로 본문 텍스트를 뽑을 수 있다.** 의존성 0으로 완결 가능. |

### citecheck-인용DOI검증과의 경계 — 가장 주의할 인접 툴

citecheck는 이미 `.docx`와 평문 참고문헌 목록을 입력으로 받는다. **겹치는 것처럼 보이므로 선을 명확히 긋는다.**

| | citecheck | draftcheck |
|---|---|---|
| 읽는 것 | 원고의 **참고문헌 목록** | 원고의 **본문 전체 + 목록** |
| 묻는 질문 | "이 문헌이 **바깥 세상에** 실존하고 철회되지 않았나?" | "이 문서가 **자기 안에서** 앞뒤가 맞나?" |
| 네트워크 | 필요 (Crossref/PubMed) | **절대 안 씀** |
| 대표 검출 | 깨진 DOI, 철회 논문, 프리프린트, 메타데이터 불일치 | 본문 인용 ↔ 목록 불일치, Figure 미언급, 숫자 불일치, 통계 보고 누락 |

즉 citecheck는 **문헌의 진위**, draftcheck는 **문서의 정합성**이다. 둘은 서로를 대체하지 않는다.

- **draftcheck는 DOI 검증을 절대 재구현하지 않는다.** 대신 추출한 참고문헌을
  **citecheck 입력 스키마와 동일한 CSV로 내보내고**, 리포트 말미에 다음 단계 명령을 문자열로 안내한다 → 두 툴이 파이프로 이어진다.
- **빌더 주의:** citecheck의 `.docx` 추출기를 참고는 하되 **import 하거나 수정하지 말 것** (툴 간 독립성이 이 저장소의 규약).
  draftcheck는 자체 `docio.py`를 갖는다.

## 범위

### 한다 (v1 점검 항목 7종)

1. **인용 ↔ 참고문헌 교차 대조**
   - 본문에서 인용됐으나 목록에 없는 번호 (`[27]` 존재, 목록은 26개까지)
   - 목록에 있으나 본문에서 한 번도 인용되지 않은 항목 (← 리뷰어 단골 지적)
   - 번호형 스타일에서 **첫 등장 순서가 오름차순이 아닌 지점** (밴쿠버 규칙 위반)
   - 저자-연도형(`(Kim et al., 2024)`)은 목록의 저자·연도와 대조
2. **Figure / Table 번호 정합**: 본문 미언급 그림·표, 존재하지 않는 번호 언급, 첫 언급 순서 역전, 번호 건너뜀
3. **숫자 일관성**: 초록 / 본문 / 표 캡션에 등장하는 **동일 라벨의 숫자가 서로 다른 경우**를 후보로 보고
   (예: 초록 `N=48` vs 본문 `48명` vs Table 1 `N=45`). 확정이 아니라 **불일치 후보 제시**.
4. **통계 보고 완결성**: `p = 0.000` / `p < 0.05`만 있는 문장 / 효과크기·95% CI 없이 p값만 있는 문장 /
   p값 소수점 자릿수 혼재(`p=.03` vs `p=0.030`) — 저널 통계 리뷰어가 반드시 잡는 것들
5. **약어**: 정의 없이 처음부터 쓰인 약어, 정의만 하고 다시 안 쓴 약어, 같은 약어 재정의
6. **분량**: 제목 문자수, 초록 단어수, 본문 단어수(참고문헌·캡션 제외), 참고문헌 개수, 그림/표 개수
   → `--limits` JSON(저널 한도)과 대조. 한도 파일 없으면 계수만 보고.
7. **인식 실패 자체를 보고**: 인용 토큰을 0개 찾았거나 참고문헌 목록을 못 찾으면 **"이상 없음"이 아니라 "점검 불가"로 크게 경고**.
   (조용히 통과시키는 체커는 없느니만 못하다. 이건 완료 기준에 포함.)

### 의도적으로 **안 한다**

- 영문 교정·문법·표현 다듬기 (Grammarly/DeepL 영역)
- 논문 내용·논리·과학적 타당성 평가 (사람의 일)
- DOI가 실제 존재하는지 검증 (→ **citecheck**로 넘김. 네트워크 절대 안 씀)
- 참고문헌 스타일 자동 변환(밴쿠버↔APA) — **감지만 하고 변환은 안 함**
- 저널별 템플릿 자동 서식 적용, 표절 검사, PDF 생성
- 원고 자동 수정 — **읽기 전용. 원본 파일은 절대 건드리지 않는다.**
- 저널 한도 DB 내장 (금방 낡는다). 소수의 예시 프로파일 + 사용자 지정 JSON만.

## 입력 / 출력

### 입력

- **원고 파일**(필수): `.docx` (stdlib `zipfile`+`xml.etree`로 `word/document.xml` 파싱) / `.md` / `.txt` / `.tex`
- **저널 한도**(선택): `--limits journal.json`
  ```json
  {
    "journal": "Sleep Medicine",
    "title_chars_max": 120,
    "abstract_words_max": 250,
    "body_words_max": 4000,
    "references_max": 50,
    "figures_tables_max": 6
  }
  ```
- **옵션**: `--citation-style auto|numeric|author-year`, `--out-dir OUT`, `--strict`(문제 발견 시 exit code 1)

### 실행 예

```bash
draftcheck 원고.docx --limits journals/sleepmed.json --out-dir 점검_20260806
```

### 출력 (3종)

**1) 콘솔 요약 (한국어)**
```
draftcheck — 원고.docx (본문 3,812단어 / 인용 스타일: numeric 자동판별)

■ 치명 3건
  L142  인용 [27]이 참고문헌 목록에 없습니다 (목록은 26개)
  L 88  Figure 3이 본문에서 한 번도 언급되지 않았습니다
  L 31  초록 "N = 48" ↔ 본문 L207 "45명" ↔ Table 1 "N = 45" — 숫자 불일치 후보

■ 경고 9건
  L156  p = 0.000 → "p < 0.001"로 보고해야 합니다
  L163  p값만 있고 효과크기·95% CI가 없습니다
  L 47  약어 'ISI'가 정의 없이 사용되었습니다 (첫 정의는 L119)
  ...

■ 분량 (Sleep Medicine 기준)
  초록 268단어 / 한도 250  ✗ 18단어 초과
  본문 3,812단어 / 한도 4,000  ✓
  참고문헌 26개 / 한도 50  ✓

치명 3 · 경고 9 · 통과 5  →  점검_20260806/점검결과.md
```

**2) `점검결과.md`** — 항목별 근거와 줄번호가 붙은 한국어 리포트 (공저자에게 그대로 전달 가능)

**3) `문제목록.csv`** — `줄번호, 심각도, 유형, 대상, 설명, 권고`
   (심각도: 치명/경고/정보 · 유형: 인용누락/미인용문헌/그림미언급/숫자불일치/통계보고/약어/분량)

**4) `references.csv`** — `Study ID, Authors, Year, Title, Journal, Article DOI, PMID`
   ← **citecheck-인용DOI검증의 입력 스키마와 동일.** 바로 이어서 돌릴 수 있음. (파싱 실패한 항목은 빈 칸 + `parse_ok` 열로 표시)

## 실패할 수 있는 지점 (그리고 가장 싸게 조기 발견하는 법)

**1) 실제 원고의 .docx가 EndNote 필드·추적변경·각주로 뒤덮여 인용 토큰 추출이 깨진다. — 가장 큰 위험.**
합성 예제에서는 100% 잘 되고 진짜 원고에서는 0%일 수 있다.
→ **가장 싼 조기 확인:** 빌드 초반 30분 안에 `docio.py`만 먼저 만들고, `--dump-text` 로 텍스트+인용 토큰 인식 수를 출력하게 한 뒤
   **사용자의 실제 원고 .docx 한 개**에 돌려본다. 인용 토큰이 0개거나 본문이 잘려 나오면, 그 자리에서
   `.docx` 지원을 "본문 추출만 보장, 필드 인용은 미지원"으로 정직하게 축소하고 `.md`/`.tex`를 1급 포맷으로 재배치한다.
   (추적변경이 남아 있으면 `w:del` 텍스트를 반드시 제외해야 한다 — 삭제된 문장의 인용을 세면 전부 틀린다.)

**2) 숫자 일관성 점검(항목 3)이 거짓 양성 폭탄이 된다.**
"N=48"과 무관한 "48세"를 같은 값으로 묶으면 리포트가 소음이 되고, 그 순간 이 툴은 두 번 다시 안 열린다.
→ **조기 확인:** 라벨 패턴을 아주 좁게 시작한다(`N =`, `n =`, `참가자 N명` 같은 명시적 라벨만).
   깨끗한 대조본에서 이 항목의 치명이 1건이라도 나오면 **규칙을 넓히지 말고 좁힌다.**
   최악의 경우 항목 3을 `정보` 등급으로 강등하거나 v1에서 통째로 뺀다 — **나머지 6개 항목만으로도 이 툴은 값어치를 한다.**

**3) 저자-연도 스타일 지원이 반쪽이 된다.**
`(Kim & Lee, 2024)`, `(Kim et al., 2024a)`, `Kim 등(2024)` 변형이 끝없다.
→ v1은 numeric을 1급, author-year를 2급으로 명시하고, 인식률을 출력에 숫자로 찍는다.
   "인식된 인용 12 / 추정 40" 처럼 **자기 커버리지를 스스로 보고**하게 하면 사용자가 신뢰 여부를 즉시 판단할 수 있다.

**4) 근본적 무용지물 시나리오: 사용자가 사실 이 확인을 이미 공저자/에디팅 업체에 맡기고 있다.**
→ 이건 코드로 확인할 수 없다. 가장 싼 확인은 **첫 실행 결과 자체**다.
   실제 원고 1개에 돌려서 치명 0건·경고 0건이 나오면 이 툴은 필요 없었던 것이고, 그 사실을 30초 만에 알 수 있다.
   반대로 리뷰어에게 지적당했을 법한 항목이 하나라도 나오면 그걸로 투자 회수는 끝난다.

- 이름/폴더: `draftcheck-원고투고점검`, 파이썬 패키지 `draftcheck` (기존 17개 패키지명과 충돌 없음 — 확인할 것)

- 우선순위가 밀리면 버릴 순서: 항목 3(숫자 일관성) → 항목 6(분량 한도 대조) → 항목 5(약어).
  **절대 버리면 안 되는 것: 항목 1(인용 교차 대조)과 항목 7(인식 실패 보고).** 이 둘이 이 툴의 존재 이유다.
