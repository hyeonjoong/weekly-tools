# numcheck — 원고 수치 재계산 검증

원고(.docx/.md/.tex/.txt) 하나를 받아 **본문에 적힌 숫자 중 알아볼 수 있는 것을 전부 다시 계산해** 대조하는 오프라인 CLI. 데이터 파일도, 네트워크도, 외부 라이브러리도 필요 없습니다.

"전부"라고 쓰지 않은 것은 의도적입니다. 실제 원고에서 재계산에 도달하는 비율은 **인식된 후보의 60~90%**, 원고에 적힌 숫자 전체로 보면 그보다 낮습니다. 그래서 이 툴은 매 실행마다 **몇 개를 봤고 몇 개를 못 봤는지 먼저 말합니다** — 그 자백이 이 툴의 존재 조건입니다(아래 [커버리지 자백](#커버리지-자백--이-툴의-존재-조건)).

---

## 목적 / Why this exists

**한국어.** 금요일 밤, 공동저자가 보낸 리비전 원고를 엽니다. 3주 전 데이터가 갱신되면서 분석 N 이 바뀌었고, Results 표는 새로 붙여 넣었습니다. 남은 것은 손으로 고친 흔적들입니다 — Abstract 의 `23/48 (45.2%)`(다시 나눠 보면 47.9%), Table 2 의 `총 48명 (능동 24, 대조 23)`(합이 47), `t(45) = 2.31, p = .003`(그 통계량에서 나오는 p 는 .026), `ISI 평균 14.37 (N = 23)`(23명의 정수 합으로는 나올 수 없는 평균). 통계는 다시 돌렸으니 맞고, 표도 나오고, 문장도 읽힙니다. **틀린 건 숫자뿐이고, 그건 티가 안 납니다.** 논문 한 편에 숫자 claim 이 100~300개인데 사람이 전수 재계산하는 일은 실제로 일어나지 않습니다 — 리비전마다 반복되면 더더욱. 이 툴은 그 전수 대조를 대신합니다. 임상시험 원고를 리비전하는 연구자, 공동저자 초고를 검토하는 교신저자, 심사를 의뢰받은 리뷰어가 **투고 버튼을 누르기 전 30초** 동안 씁니다.

**English.** After a data refresh the tables get repasted, but the hand-edited numbers around them do not survive intact: `23/48 (45.2%)` when the division gives 47.9%, `48 patients (24 active, 23 control)` when the subgroups sum to 47, `t(45) = 2.31, p = .003` when that statistic yields p = .026, `ISI mean 14.37 (N = 23)` when no set of 23 integer sum-scores can average to that. A paper carries 100–300 numeric claims; nobody recomputes them by hand, least of all at every revision. numcheck recomputes all of them: proportions against their own numerator/denominator, reported *p* values against the reported test statistic and df, subgroup Ns against the stated total, means of integer scales against what is arithmetically attainable at that N (GRIM/GRIMMER), change scores against post − pre, and confidence intervals against their own point estimate and *p*. It is for the clinical researcher revising a manuscript, the corresponding author checking a co-author's draft, and the reviewer who wants the arithmetic settled before reading the argument — **in the 30 seconds before you hit submit.** Offline, read-only, zero dependencies.

### 이 툴이 statcheck / LLM 과 다른 점

| | numcheck | statcheck (R) | LLM 에 붙여넣기 |
|---|---|---|---|
| p 재계산 | ✅ 자체 구현 CDF | ✅ | ❌ **값을 지어냅니다** |
| 비율·N 합계·GRIM·변화량·CI | ✅ | ❌ p 만 | ⚠️ 자주 틀립니다 |
| 한국어 원고·표 안 숫자 | ✅ | ❌ APA 영문 표기만 | ⚠️ |
| 몇 개를 못 봤는지 말함 | ✅ **필수 출력** | ❌ | ❌ 세지도, 못 셌다고 말하지도 않습니다 |
| 반올림 오탐 방어 | ✅ 구간 비교 + 자동 강등 | ⚠️ 오탐이 많기로 유명 | — |
| 설치 | Python 표준 라이브러리만 | R 필요 | — |

`draftcheck`(형식이 갖춰졌는가)·`citecheck`(문헌이 실재하는가)와 함께 **원고 3종 세트**로 씁니다. numcheck 가 묻는 것은 하나뿐입니다 — **산술이 맞는가.**

## 사용법

```bash
numcheck 원고_revision2.docx                       # 콘솔 리포트만
numcheck 원고_revision2.docx --out-dir 검토_20260813 # CSV 2종 + 요약 저장
numcheck 원고.docx --scale ISI=0:28:7               # GRIM 켤 척도 추가
numcheck 원고.docx --scale-config scales.json       # 척도를 파일로 관리
numcheck 원고.docx --lang en                        # 영문 리포트
numcheck 원고.docx --dump-text | less               # 무엇을 읽었는지 확인
numcheck 원고.docx --out-dir 검토 --force           # 출력 폴더의 남의 파일도 덮어쓰기
```

## 무엇을 검사하는가

| 항목 | 무엇을 묻는가 | 예 |
|---|---|---|
| **비율 재계산** | 적힌 백분율이 그 분자/분모에서 나오는가 | `23/48 (45.2%)` → 47.92% |
| **p 재계산** | 보고된 통계량과 자유도에서 그 p 가 나오는가 | `t(45)=2.31, p=.003` → .0255 |
| **N 합계** | 하위군 합이 전체와 같은가 | `총 48명 (24, 23)` → 47 |
| **GRIM / GRIMMER** | 그 N 에서 그 평균(·SD)이 **존재할 수 있는가** | ISI 14.37, N=23 → 불가능 |
| **변화량** | 사후 − 사전 이 적힌 변화량과 맞는가 | `18.4 → 11.2 (변화 -5.2)` |
| **신뢰구간** | 점추정치가 자기 CI 안에 있는가, 상·하한이 안 뒤바뀌었는가 | `-6.8 (CI -5.9 ~ -1.1)` |
| **CI ↔ p** | CI 가 귀무값을 포함하는데 유의하다고 하지 않는가 | `1.2 (CI -0.4~2.8), p=.03` |
| **유의성 문구** | `p = .07` 인데 "유의하게" 라고 쓰지 않았는가 | |
| **불가능한 통계량** | 그 값이 존재할 수 있는가 | `r(38) = 1.5`, `t(0)`, `χ²(3) = -5` |

### 등급 3단계와 판정 근거

| 등급 | 언제 | 종료코드 기여 |
|---|---|---|
| **치명** | 반올림·버림·올림을 **모두 허용해도** 산술이 맞지 않는다. 정당한 사유가 될 만한 단서도 없다. | 1 |
| **경고** | 어긋나 보이지만 정당할 수 있다 — 단측검정·다중비교 보정 단서가 근처에 있음, 분모를 문맥에서 **추정**함, 검정과 구간추정의 방법이 다를 수 있음, 차이가 근소하고 유의성 판정이 안 바뀜, GRIMMER(SD 정의·중도절단 등 예외 가능). **강등 사유를 반드시 함께 출력합니다.** | 2 |
| **정보** | 검사하지 못했지만 사용자가 지정하면 검사할 수 있다(척도 미지정 등). | 0 |

### 종료코드

`0` 문제 없음 · `1` 치명 있음 · `2` 경고만 있음 · `3` **입력 처리 불가**(파싱 실패, 재계산 가능 claim 이 `--min-checked`(기본 5)개 미만, **또는 원고의 일부를 잘라 냈을 때**). 조용히 "이상 없음"을 내지 않습니다.

잘림이 왜 `0` 이 아니라 `3` 인지: 20,000자를 넘는 문단·표 행이나 400,000줄을 넘는 파일은 뒷부분을 버립니다. 그 뒤에 오류가 있었는지는 **알 수 없으므로**, 메모에만 적고 `0`(이상 없음)을 내면 그건 거짓말입니다.

### 커버리지 자백 — 이 툴의 존재 조건

리포트 첫 문단은 **항상** `검사 후보 N개 · 재계산 M개 · 건너뜀 K개` 와 사유별 내역입니다. `재계산표.csv` 에는 **건너뛴 것까지 전부** 한 줄씩 들어 있어 사람이 직접 검산할 수 있습니다. 몇 개를 못 봤는지 말하지 않는 체커는 "이상 없음"이라는 말로 거짓말을 하게 됩니다.

### 출력 파일 (`--out-dir`)

- `문제목록.csv` — `줄번호,절,등급,항목,원문,보고값,재계산값,판정,설명` (draftcheck 의 지적 목록과 같은 모양)
- `재계산표.csv` — 커버리지 요약 몇 행 + **모든** claim 후보와 처리 결과
- `요약.txt` — 콘솔 리포트 전문

## GRIM 을 쓰려면

GRIM 은 개인 점수가 **이산적**일 때만 성립합니다. ISI 는 7문항 0–4점 정수 합이므로 N = 23 명의 평균은 반드시 (정수)/23 꼴입니다. 나이·BMI·수면시간에 같은 규칙을 적용하면 헛소리가 됩니다.

그래서 numcheck 는 **척도를 추측하지 않습니다.** 등록된 이름이 문장에 명시적으로 있을 때만 GRIM 을 켭니다.

내장 척도: `ISI` `PSQI` `ESS` `PHQ-9` `GAD-7` `HADS`(총점 0–42) `HADS-A` `HADS-D` `PSS` `BDI-II` `FSS` `MMSE` `MoCA`

추가하려면:

```bash
numcheck 원고.docx --scale ISI=0:28:7 --scale 나만의척도=0:60:15
numcheck 원고.docx --scale 단어인지도=0:100:50 --percent-of-count 단어인지도
```

```json
// scales.json  →  --scale-config scales.json
{ "ISI":      { "min": 0, "max": 28, "items": 7 },
  "단어인지도": { "min": 0, "max": 100, "items": 50, "percent_of_count": true,
               "aliases": ["word recognition score", "WRS"] } }
```

`percent_of_count` 는 "고정 목록 대비 정답 백분율"입니다. 50문항이면 개인 점수가 2%p 단위이므로 N 명의 평균은 2k/N 꼴이어야 합니다.

### GRIM 이 침묵하는 경우 — 먼저 알아 두세요

가능한 평균들의 간격은 `1/N` 입니다. 이 간격이 **반올림 허용 폭보다 좁으면** 어떤 평균이든 항상 후보가 있어 GRIM 은 아무것도 가려내지 못합니다. 실무적으로는 대략 **N < 10^(소수 자릿수) / 2** 일 때만 판별력이 있습니다.

| 보고 자릿수 | 판별력이 있는 N |
|---|---|
| 소수 1자리 (`14.4`) | N ≲ 5 |
| 소수 2자리 (`14.37`) | N ≲ 50 |
| 소수 3자리 (`14.372`) | N ≲ 500 |

즉 **N = 56/군인 시험에서 평균을 소수 1~2자리로 보고하면 GRIM 은 거의 매번 침묵합니다.** 그때 리포트에는 `건너뜀 사유: 판별력 없음` 이 찍히므로, 조용히 "통과"로 오해할 일은 없습니다. GRIM 은 이 툴의 보너스 항목이고, 실전 가치의 대부분은 p 재계산·비율·CI·유의성 문구에서 나옵니다.

## 한계 (솔직하게, 길게)

**PDF 는 지원하지 않습니다(v1).** 표준 라이브러리만으로 PDF 텍스트 레이아웃을 신뢰성 있게 뽑는 것은 한 세션에 끝나지 않고, **반쯤 되는 파서는 커버리지 자백을 거짓말로 만듭니다** — 표가 뒤섞여 읽히면 "137개를 검사했다"가 사실이 아니게 됩니다. 편집 가능한 원본(.docx/.md/.tex/.txt)에 실행하세요. v2 1순위 항목입니다.

**표 파싱에는 구조적 한계가 있습니다.** `.docx` 표는 행 단위로 셀을 `|` 로 이어 붙여 읽습니다. 그래서 같은 행 안의 숫자끼리는 대조되지만, **머리행의 `n = 23` 이 어느 열에 걸리는지는 추측하지 않습니다.** 표 안 GRIM 은 셀에 `14.37 (N = 23)` 처럼 N 이 함께 적혀 있을 때만 돌아갑니다. 병합 셀·세로쓰기·각주 기호가 섞인 복잡한 표는 그만큼 커버리지가 떨어지며, 그 사실은 리포트의 "건너뜀" 집계에 그대로 드러납니다.

**단측검정 오탐 가능성이 남아 있습니다.** statcheck 이 실제로 겪은 문제입니다. numcheck 는 (a) 통계량의 반올림 구간 전체에서 p 범위를 계산하고, (b) 단측·보정 키워드가 같은 문장에 있으면 치명을 경고로 강등하며, (c) 키워드가 없어도 **단측으로 계산했을 때 값이 맞아떨어지면** 강등합니다. 그래도 키워드가 문장을 넘어가 있거나(앞 문단의 "all tests were one-tailed"), 표 안에서 보정된 p 만 제시된 경우에는 경고가 뜰 수 있습니다. **경고는 "확인해 보라"는 뜻이지 "틀렸다"가 아닙니다.**

**보정·대체된 평균에는 GRIM 을 돌리지 않습니다.** 공분산분석 조정평균, MMRM 추정 주변평균(LSMean), 다중대입·LOCF 로 대체한 뒤의 평균, 기하·절사·가중 평균은 개인값이 정수가 아니거나 정수 합의 산술평균이 아니므로 GRIM 의 전제가 성립하지 않습니다. 이런 단서가 **같은 문단 안에** 있으면 건너뛰고 `원자료 평균 아님` 으로 기록합니다. SERENE 의 1차 지표(ISI)는 MMRM 보정평균으로 보고될 가능성이 높으므로, 이 자리에서 오탐이 나면 툴 전체의 신뢰가 무너집니다 — 그래서 넓게 잡았고, 그만큼 **진짜 위반도 일부 놓칩니다.** 원자료의 산술평균임이 분명하면 그 문장에서 보정 단어를 빼고 다시 돌리세요.

**p 재계산의 실효 허용폭은 생각보다 넓습니다.** 보고된 통계량과 보고된 p **양쪽**에 반올림 구간을 주므로, `t(45) = 2.31`(참값 p = .0255)에서는 `p = .026`·`.024`·`.03`·`.02` 가 모두 통과합니다. 소수 2자리로 적은 `p = .02` 는 사실상 ±.01 까지만 검사되는 셈입니다. 이건 오탐을 죽이기 위한 의도된 설계이지만, **민감도를 과대평가하지 마세요.** 더 엄격하게 보려면 `--tolerance 0.5`(반올림만 허용, 버림·올림 불허)를 쓰되 오탐이 늘어납니다.

**문맥에서 추정한 분모는 틀릴 수 있습니다.** `23명 (47.9%)` 처럼 분모가 문장에 없으면 같은 줄/앞 줄에서 전체 N 을 찾습니다. 후보가 **정확히 하나일 때만** 쓰고, 그 지적은 항상 경고입니다. 후보가 둘 이상이면 추측하지 않고 "분모 없음"으로 건너뜁니다.

**통계 방법이 옳은지는 판단하지 않습니다.** t-검정을 썼어야 했는지, 다중비교 보정이 필요한지는 사람의 일입니다. numcheck 는 **산술만** 봅니다.

**원본 데이터를 읽지 않습니다.** 원고에 적힌 숫자끼리만 대조합니다. 데이터에서 다시 분석하는 것은 `statwise`/`longistat` 의 일입니다.

**참고문헌↔본문 대조·그림/표 번호·약어·단어수·초록↔본문 표본수(N) 일관성·통계 보고 형식(p=0.000, 효과크기/CI 누락 등)**은 `draftcheck`, **DOI 검증**은 `citecheck` 의 일입니다. 여기서 재구현하지 않습니다. 특히 **N 일관성과 통계 보고 형식은 draftcheck 와 주제가 겹칩니다** — 다만 draftcheck 는 *존재·일치 여부*만 보고 numcheck 는 *산술*만 봅니다. 두 툴은 서로를 import 하지 않으며, 같이 돌리는 것이 맞습니다.

**같은 수치가 절마다 다르게 적힌 것은 잡지 못합니다.** numcheck 는 각 claim 을 **자기 안에서만** 대조합니다. 초록의 `23/48 (47.9%)` 는 그 자체로는 산술이 맞으므로, 본문의 최종 N 이 46 이라도 여기서는 통과합니다. 절 사이의 표본수 불일치(초록↔본문 N)는 `draftcheck` 의 항목이고, 이 저장소의 규칙상 재구현하지 않습니다. **두 툴을 같이 돌리세요.**

**커버리지 자백은 "인식한 후보"만 셉니다.** 표기를 아예 알아보지 못한 숫자는 "건너뜀"에도 잡히지 않습니다(그건 원리적으로 셀 수 없습니다). 그래서 후보 수가 원고 규모에 비해 터무니없이 적으면 그 자체가 신호이고, 재계산 가능 claim 이 `--min-checked` 미만이면 아예 종료코드 3 으로 멈춥니다. `--dump-text` 로 무엇을 읽었는지 직접 확인할 수 있습니다.

**LaTeX 은 `\%`·`\pm`·`\times` 등 흔한 이스케이프만 풉니다.** 매크로를 많이 쓴 `.tex` 는 그만큼 인식률이 떨어지며, 그 사실은 후보 수에 드러납니다.

**`--lang en` 은 리포트를 영문으로 냅니다 — 다만 원문 발췌는 원고 언어 그대로입니다.** 한국어 원고를 영문 리포트로 뽑아도 인용된 문장은 한국어입니다(그게 원고니까요).

**의도적으로 판단을 접는 자리가 있습니다.** 한 문장에 성격이 다른 '차이'가 섞여 있거나(군간 차이 + 변화량), 한 문장에 p 가 둘 이상이거나, 신뢰구간의 경계가 귀무값에서 반올림 오차 안에 있으면 **검사하지 않고 건너뜀으로 기록합니다.** 애매한 자리에서 지적하는 쪽보다 침묵하는 쪽을 골랐고, 침묵했다는 사실은 커버리지 자백에 남습니다.

**진짜 원고에서 0건이 나올 수도 있습니다.** 통계를 자동화해 왔다면 p 와 비율이 이미 맞을 수 있습니다. 그때는 이 툴이 필요 없었다는 뜻이고, 그것도 30초 만에 알 수 있는 유용한 정보입니다. 다만 **초고가 아니라 리비전을 거친 최종 제출본**에 돌려 보세요 — 걸릴 확률이 훨씬 높습니다.

## 안전성

- **네트워크 호출 0.** 소스에 `urllib`/`socket`/`requests` 가 아예 없으며, 그 사실을 테스트가 정적으로 검사합니다.
- **원본 읽기 전용.** 원고 파일을 쓰기 모드로 여는 코드 경로가 없습니다. 출력은 `--out-dir` 안에만 만듭니다(테스트가 mtime 까지 확인).
- **CSV 수식 인젝션 방어.** `=` `+` `-` `@` 로 시작하는 셀 앞에 `'` 를 붙입니다. 단 `-7.4` 처럼 숫자로 읽히는 값은 그대로 둡니다(수식이 아니고, 전부 따옴표를 붙이면 표를 쓸 수 없습니다).
- **오류 메시지에 원고 내용을 넣지 않습니다.** 파일명·줄번호·항목명만 남깁니다. 지적 문구에는 문제가 된 **숫자와 그 주변 발췌**가 들어가며(그게 지적의 본체입니다), 남에게 보낼 때는 `--no-quote` 로 발췌를 뺄 수 있습니다.
- **zip bomb / XML bomb 방어.** `.docx` 의 DTD·ENTITY 선언과 UTF-16 파트(바이트 검사를 우회하는 통로)는 거부하고, 압축 해제 크기·멤버 수·중첩 깊이·**XML 노드 수**에 상한이 있습니다.
- **남의 파일을 덮어쓰지 않습니다.** 출력 폴더에 같은 이름의 파일이 있는데 그것이 이전 numcheck 산출물이 아니면, 쓰지 않고 멈춥니다(`--force` 로 강제). 출력 대상이 심볼릭 링크면 거부합니다 — 링크를 따라가면 `--out-dir` 바깥을 쓰게 되기 때문입니다.
- **인자 오류의 종료코드는 3 입니다.** 2 는 "경고만 있음"이라, CI 가 실행되지도 않은 run 을 통과로 읽는 일이 없도록 했습니다.

## 정확도 근거

t / F / χ² / z / r 의 꼬리 확률은 불완전 베타·감마를 직접 구현해 계산합니다(scipy 불필요). `dev/verify_against_scipy.py` 로 격자 대조(고정 격자 + 무작위 4,000점)한 결과 **최대 상대오차는 t 3.4e-10 · F 2.6e-10 · χ² 5.5e-11 · z 1.3e-13 · r 3.3e-13** 로, 이 저장소의 기준(≤1e-9)을 만족합니다. 이 보장은 **자유도 50,000 이하**에서의 것입니다 — 그보다 크면 `lgamma` 차이에서 상대정밀도가 깎여 기준을 넘으므로, 값을 내놓는 대신 **그 claim 을 건너뜁니다**(원고에 df > 50,000 이 적히는 일은 없습니다). 그 스크립트는 개발용이며 런타임 의존성이 아닙니다.
